# Planning

## Классификация задачи

**Простая задача** (планирование не нужно): единичное, понятное изменение.
- Отметь в тексте командой `\mytodo{...}` (или `\fixit`/`\mycomment`, где уместно). Issue не создавай.

**Сложная задача** (нужно планирование): многоступенчатая, неоднозначная или затрагивающая несколько мест.
1. Создай issue: `gh issue create --label task` (батч связанных — `--label hub` + sub-issues, см. `workflow-management`).
2. В тексте в нужном месте поставь `\mytodo{Короткое описание (issue \#N)}` — короткое описание + номер issue.
   - ⚠️ `#` экранируй как `\#`: аргументы команд todonotes — «просто текст», иначе пакет ломается.
   - Не ставь эти команды внутри окружений `definition`, `theorem`, `example`, `figure` — ломается компилятор. Ставь в ближайшее место снаружи.
3. В issue добавь строку привязки: `Привязка: \mytodo{Короткое описание}` (цитата описания mytodo).

Связи: текст→issue по номеру в mytodo; issue→текст по стабильному описанию mytodo (ищется grep'ом). **Нигде не зависит от номеров строк.**

Закрытие: убери mytodo из текста + `Closes #N` в коммите + закрой issue.

## Глобальный план (батч)
`tasks/global_plan.md` — единственный source of truth для батча. Должен:
- называть hub-issue;
- перечислять все задачи с ID, номерами issue (`#N`), кратким описанием и статусом (`[done #N]` после интеграции);
- указывать integration branch;
- отмечать зависимости между задачами;
- отмечать потенциальные конфликты/пересечения (две задачи правят один файл);
- отмечать общую инфраструктуру (команды, стили, фигуры), нужную нескольким задачам;
- отмечать переиспользуемые абстракции (см. `reusing`);
- предлагать порядок выполнения, минимизирующий переделки.

Зеркалируется в hub-issue комментарием с первой строкой `<!-- global-plan -->`.

## Detailed plan (атомарные сабтаски)
`tasks/detailed_plan.md` разбивает задачу на атомарные сабтаски. Каждый сабтаск:
- мал, чтобы завершить за одну сфокусированную сессию (обычно 30–90 минут);
- даёт собираемый, проверяемый прирост — без незакоммиченных полузаготовок;
- имеет уникальный идентификатор (S1, S2, ...), используемый в коммитах и плане.

Формат сабтаска (все секции обязательны; сабтаск без них неполный и не выполняется):

```
### SN: <заголовок>

**Code:** <файлы .tex для создания/изменения, окружения, команды>
**Figures:** <tikz-фигуры: создать/перенести, инструмент (FLPQ/UCFS/dot2tikz)>
**Docs:** <какие docs обновить: book-structure, glossary, papers — см. `documentation`>

**Spec:**
- <подробная спецификация реализации>
```

Перед detailed plan загрузи `reusing` и прогони чек-лист переиспользования.

## Granularity
Если сабтаск нельзя закоммитить как самостоятельный прирост — он слишком большой, разбей. Формат коммита — в `git-workflow`.

## Bounded uncommitted work
Незакоммиченная работа на feature-ветке никогда не превышает один атомарный сабтаск.

## Task Authoring
При создании issue (`--label task`):
- задай формат результата заранее (если задача даёт артефакты — рисунки, таблицы — укажи точный вид);
- одна задача = одна ответственность (больше 5 подпунктов или несколько независимых тем — разбей);
- укажи требования к неизменности (например, «не менять обозначения, принятые в книге»);
- укажи ожидания по переиспользованию (какие существующие объекты/примеры использовать).
