# Workflow Management

Топ-уровневый цикл, оркестрирующий остальные workflow-скиллы. Для одной задачи загружай этот скилл первым; он указывает, какой скилл за какой шаг отвечает.

## Core Rules
- Все задачи логируются как GitHub issues с меткой `task` (`gh issue create --label task`). Описание — как дал пользователь, минимальные изменения (только разбиение и нумерация). ID задачи = номер issue.
- Батч **связанных** задач отслеживается одним **hub**-issue (метка `hub`). Hub несёт глобальный план и никогда не выбирается как задача; task-issues прикрепляются к hub как GitHub **sub-issues** через REST API (`POST repos/$REPO/issues/<HUB>/sub_issues`). Перечисление номеров задач в теле hub — **не** замена sub-issue.
- Глобальный план активного батча — в `tasks/global_plan.md` (единственный source of truth), зеркалируется в hub-issue комментарием, первая строка которого `<!-- global-plan -->`. Прогресс задач отмечается в файле, зеркало обновляется после каждой интегрированной задачи (как detailed plan — см. `subtask-loop`).
- **Integration branch** определяется один раз за сессию: `INTEGRATION=$(git config --get book.integrationBranch || echo dev)`. По умолчанию `dev`. Никогда не коммить напрямую в integration branch.
- Задачи делаются строго **по одной**. На каждую задачу — своя feature-ветка (от integration branch), свой detailed plan, свой шаг интеграции. Никогда не объединяй несколько задач в одну feature-ветку.
- В батче из нескольких задач каждая выполняется в **отдельном сабагенте**: свежая сессия со своим контекстом, которая загружает этот скилл и прогоняет цикл ровно для одной задачи (шаги 3–10). Сабагенты — строго последовательно. Оркестрирующая сессия владеет батч-шагами (0–2), подтверждениями мержа и финализацией; она не выполняет шаги задачи inline.
- Каждое решение документируется до реализации. Документация должна быть достаточно подробной, чтобы воспроизвести работу и понять, почему принято каждое решение.
- Сообщения коммитов — достаточно подробные, чтобы понять причины изменений.
- Задача только по документации/тексту (без изменения, влияющего на сборку) всё равно проходит полный цикл: одна задача на ветку, один коммит на сабтаск, ревью, сборка.

## Working Loop
0. Если пользователь просит несколько связанных задач сразу — сначала настрой батч:
   a. Создай **hub**-issue (`gh issue create --label hub`).
   b. Создай по issue на задачу (`gh issue create --label task`), затем прикрепи каждый к hub как **sub-issue**:
      ```bash
      REPO=$(gh repo view --json nameWithOwner -q .nameWithOwner)
      CHILD_ID=$(gh api "repos/$REPO/issues/<N>" --jq .id)
      gh api -X POST "repos/$REPO/issues/<HUB>/sub_issues" -F sub_issue_id="$CHILD_ID"
      ```
      Проверь родителя: `gh api "repos/$REPO/issues/<N>/parent" --jq .number` должен вывести номер hub.
   c. Напиши глобальный план в `tasks/global_plan.md` (см. `planning`), назови hub и перечисли задачи с номерами issue.
   d. Опубликуй глобальный план комментарием на hub, первая строка `<!-- global-plan -->`.
1. Убедись, что задачи, глобальный план и структура книги согласованы.
2. Выбери ровно ОДНУ открытую `task`-issue, ещё не выполненную. Задача выполнена, когда коммиты её сабтасков на integration branch. Кандидаты: `gh issue list --label task --state open`.
3. Создай feature-ветку для этой одной задачи от integration branch (см. `git-workflow`).
4. Сгенерируй detailed plan в `tasks/detailed_plan.md`, разбей задачу на атомарные сабтаски (см. `planning`), опубликуй комментарием на task-issue, первая строка `<!-- detailed-plan -->`.
5. Загрузи `subtask-loop` и выполни каждый сабтаск по его циклу.
5a. Проверь, что все сабтаски завершены и не заблокированы. Если есть `[blocked]`/`[deferred]` — STOP, задача НЕ завершена, сообщи пользователю.
5b. При продолжении частично выполненной задачи сначала проанализируй состояние: текущая ветка, закоммиченные сабтаски (`git log --oneline`), `tasks/detailed_plan.md` и `tasks/global_plan.md`, `git diff --stat HEAD.."$INTEGRATION"`. Отчитайся: «S1–S3 закоммичены, S4 в работе...».
6. После всех сабтасков — ревью всего затронутого (см. `review`). Итеративно находи и чини проблемы до нуля замечаний.
7. Загрузи `quality-gates` и прогони гейт. Должен быть PASS. Если BLOCKED — чини все падения и повторяй до PASS.
8. Интегрируй задачу (см. `git-workflow`): пуш feature-ветки и PR в integration branch (rebase + merge/fast-forward, чтобы сохранить коммиты сабтасков). Пользователь ревьюит и мержит PR вручную; продолжай только после подтверждения мержа.
9. Для батча обнови прогресс: отметь интегрированную задачу `[done #<N>]` в `tasks/global_plan.md`, обнови зеркало в hub-комментарии (как detailed plan, но с маркером `<!-- global-plan -->` и номером hub).
10. Проверь, что последний коммит сабтаска несёт `Closes #<N>` (собственный issue задачи) отдельной строкой — issue закроется, когда коммит попадёт на integration branch. Для последней задачи батча тот же коммит несёт `Closes #<hub>`.
11. Вернись к шагу 2 для следующей задачи; в батче запусти нового сабагента.
